What to look for

  • Social network, GPU top-down: the frontier explodes in the middle levels and the GPU lights up fully, but it examines every edge.
  • Direction-optimizing: the big levels flip to bottom-up (cyan pulses run from unvisited vertices to the frontier) and the time drops about 3.5×.
  • Road network: the frontier never grows; most GPU lanes stay dark while every level still pays the fixed round trip. The hybrid moves those levels to the CPU and is 5× faster.

How the clock works

Each simulated level stands for one or more real levels of LiveJournal (14 levels, 86M edge entries) or roadNet-CA (~600 levels, 5.5M). A GPU level costs 0.18 ms plus 0.4 ns per top-down edge or 0.12 ns per bottom-up edge; a CPU level costs 22 µs plus 1.6 ns per edge. These constants come from the measured runs, and the totals land within a few percent of the real results shown beside them, except the hybrid on the social graph (10.4 modelled vs 8.8 ms measured), where the toy graph has fewer tiny levels than the real one.

Problem statement

Why graphs are hard for a GPU

A GPU is fast when thousands of threads do the same work on neighbouring memory. Graph algorithms break all three of those conditions.

Irregular memory access

Following an edge means reading the data of a vertex that can live anywhere in memory. We measured that the M2 GPU streams 95 GB/s sequentially but manages only 0.28 billion random 4-byte reads per second once the data exceeds the 8 MB cache, about 40× less.

Load imbalance

Social networks have a few "hub" vertices with tens of thousands of neighbours and millions with a handful. If one thread handles one vertex, the thread that draws a hub works thousands of times longer than its neighbours.

Synchronisation

BFS proceeds level by level, and each level needs a round trip between CPU and GPU (we measured 111 µs). A road map has about 600 levels, so this cost can dominate.

Little work per byte

Both algorithms do almost no arithmetic per edge. Speed is decided by memory traffic and latency, so the relevant comparison is against memory bandwidth, not compute.

Research questions

  • How close can BFS and PageRank get to the M2's memory bandwidth, and which kernel designs get there?
  • Does Apple's unified memory, where CPU and GPU share the same RAM, make it worthwhile to split one algorithm between them?
  • How do the results compare with the best CPU code (the GAP Benchmark Suite), measured fairly on the same graphs?
  • Which of the expected effects (load imbalance, sync cost, cache, vertex order) actually show up, and why?
Background · part 1

Graphs, from the beginning

A graph is a set of things (vertices) and connections between them (edges). People and friendships, web pages and links, road junctions and roads: all of these are graphs, and many questions about them come down to a few basic algorithms.

Vertices, edges, degree

A graph G = (V, E) has n vertices and m edges. In a directed graph an edge has a direction (page A links to page B); in an undirected graph it goes both ways (a friendship). The degree of a vertex is its number of edges; directed graphs distinguish in-degree and out-degree.

Paths, distance, diameter

A path is a sequence of edges. The distance between two vertices is the length of the shortest path, counted in hops. The diameter is the largest distance in the graph. A connected component is a group of vertices that can all reach each other.

Two very different kinds of real graph

Small-world, heavy-tailed social & web

Social networks and the web have a small diameter: almost everyone is within 5–10 hops of everyone else. Their degrees are heavy-tailed (roughly a power law): most vertices have a handful of edges, a few "hubs" have tens of thousands. In LiveJournal the average degree is 14 and the largest is 20,292.

Large-world, uniform road networks

Road networks are nearly planar: every junction connects to 2–4 roads, and no vertex in roadNet-CA has more than 12. Going from one end of California to the other takes hundreds of hops, so the diameter is large (about 770).

These two shapes stress a GPU in opposite ways. Hubs create load imbalance, because one thread may get thousands of times more work than another. A large diameter creates many tiny steps, each with a fixed cost. Most results in this project trace back to one of these two properties.

Why BFS and PageRank

Breadth-first search

Finds the hop distance from one vertex to all others. It answers "how far is everyone from me", finds connected components, and is the inner loop of many larger algorithms (betweenness centrality, maximum flow, community detection). It is also the kernel of the Graph500 ranking of supercomputers.

PageRank

Scores every vertex by how likely a random walker is to be there. It was invented to rank web pages for Google and is used for recommendation, influence, citation analysis and fraud detection. It touches every edge in every iteration, so it is a pure test of memory bandwidth.

Storing a graph in memory

Adjacency matrix: too big

An n×n table with a 1 for every edge. For LiveJournal that is 4.8 million × 4.8 million cells, about 2.9 TB even at one bit per cell, while 99.9997% of the cells are zero.

Compressed sparse row (CSR): what we use

Store only the edges. col_idx lists every vertex's neighbours back to back; row_ptr says where each list starts. That is 4 bytes per edge plus 4 per vertex: LiveJournal fits in 280 MB, Orkut in 906 MB.

vertex: 0 1 2 3 row_ptr: [ 0, 2, 5, 6, 8 ] col_idx: [ 1, 2, 0, 2, 3, 0, 1, 2 ] neighbours of vertex 1 = col_idx[ row_ptr[1] .. row_ptr[2] ) = col_idx[2..5) = {0, 2, 3} degree of vertex 1 = row_ptr[2] − row_ptr[1] = 3

Two derived versions are built when a graph is loaded. BFS treats every graph as undirected, so directed edges are symmetrized (each edge stored both ways). Pull-style PageRank needs each vertex's incoming edges, so it uses the transpose of the directed graph. Datasets arrive as text edge lists from SNAP; a converter turns them into binary CSR in two streaming passes, so even the 234-million-edge Orkut file converts within the 8 GB of RAM.

Background · part 2

Breadth-first search in depth

The serial algorithm

The textbook BFS keeps a queue. It removes a vertex, looks at its neighbours, and appends every neighbour it has not seen before. Each vertex enters the queue once and each edge is looked at once (twice for undirected graphs), so the cost is O(n + m). This is our correctness reference, cpu_serial.

dist[all] = ∞; dist[source] = 0; queue = [source] while queue not empty: v = queue.pop_front() for u in neighbours(v): if dist[u] == ∞: dist[u] = dist[v] + 1 queue.push_back(u)

Levels and the frontier

The queue naturally holds vertices in order of distance. Grouping them gives levels: level 0 is the source, level 1 its neighbours, level 2 their unvisited neighbours, and so on. The vertices of the current level are the frontier. A parallel BFS processes one whole level at a time; this is called level-synchronous BFS:

frontier = [source]; level = 0 while frontier not empty: next = [] in parallel for v in frontier: ← thousands of threads at once for u in neighbours(v): if dist[u] == ∞ and claim(u): ← only one thread may win u dist[u] = level + 1 append u to next barrier ← everyone finishes the level frontier = next; level += 1

The barrier at the end of each level is unavoidable: level k+1 depends on the whole of level k. On the GPU each barrier is a full round trip to the CPU, which is why the road network (≈600 levels) is hard.

Race conditions and atomics

The problem

Two frontier vertices can share an unvisited neighbour u. Their threads both see dist[u] == ∞ at the same moment, both write it, and both append u to the next frontier. u is now processed twice, and on high-degree graphs the duplicates multiply.

The fix: compare-and-swap

An atomic compare-and-swap (CAS) changes dist[u] from ∞ to level+1 only if it is still ∞, and tells the thread whether it succeeded. Exactly one thread wins. Metal only provides a "weak" CAS that may fail spuriously, so the kernel retries in a loop. A benign race is the exception: in gpu_vertex every racing thread writes the same value, so no atomic is needed.

Two ways to store the frontier

Queue (sparse list)

A list of vertex ids. Appending needs an atomic counter, which thousands of threads would fight over. Our kernels aggregate: the 32 lanes of a simdgroup count their new vertices, compute their offsets with one prefix sum, and a single lane performs one atomic add for all 32.

Bitmap (dense)

One bit per vertex: 1 if it is in the frontier. LiveJournal's bitmap is 4.8 million bits = 600 KB, small enough to stay in the GPU's cache. Checking "is my neighbour in the frontier?" becomes a cheap cached read. The 32 lanes of a simdgroup cover exactly one 32-bit word, so they build it with one simd_or and no atomics.

Top-down and bottom-up

Top-down push

Each frontier vertex scans its neighbours and claims the unvisited ones. Work ≈ the edges leaving the frontier. Efficient while the frontier is small.

Bottom-up pull

Each unvisited vertex scans its neighbours and stops at the first one in the frontier. When the frontier covers half the graph, most scans stop after one or two neighbours. No atomics are needed, because each vertex only writes its own distance.

Direction-optimizing BFS (Beamer, Asanović and Patterson, SC'12) picks per level. With mf = edges leaving the frontier and mu = edges of still-unvisited vertices, it switches to bottom-up when mf > mu/α, and back to top-down when the frontier shrinks below n/β vertices. We use the GAP suite's α = 15 and β = 18, and the unit tests check that the GPU makes the same choice as the CPU at every level. Step through the toy graph below and compare the two costs per level:

On LiveJournal the effect is large: the three biggest levels examine 17 million adjacency entries bottom-up instead of 82 million top-down.

Giving every thread a fair share: load balancing

Suppose the frontier holds four vertices with degrees 3, 1, 5 and 2 (11 edges in total). There are several ways to hand this work to GPU threads, and they are exactly the variants this project compares:

gpu_naive
thread per frontier vertex
Thread 3 does 5 edges while thread 2 does 1. With a 20,000-degree hub, one thread works 20,000× longer and its 31 simdgroup neighbours wait.
gpu_vertex
thread per vertex, every level
No queue at all: every vertex gets a thread and checks whether it is in the frontier. Simple, but most threads have nothing to do, and on a 600-level graph all n threads launch 600 times.
gpu_binned
degree bins
Vertices are sorted into small, medium and large bins. A simdgroup (32 lanes) shares one medium list; a whole threadgroup shares one hub's list. Big lists get many workers.
gpu_edge
fixed edges per thread
Every thread gets exactly 2 edges, whoever they belong to. Perfect balance, at the cost of a prefix sum and a small search (below).

How does a thread in gpu_edge know which edges are its own? An exclusive prefix sum (scan) of the frontier degrees gives each vertex's starting position in one long virtual list of edges:

Thread t handles virtual edges 2t and 2t+1. Thread 2, for example, gets edges 4 and 5; a binary search in the offsets [0, 3, 4, 9] shows that both belong to vertex C. The scan itself runs on the GPU in three phases: each threadgroup scans its block, one group scans the block totals, and every block adds its offset back.

The hybrid: using both processors

Because the M2's CPU and GPU share memory, a BFS level can run on either one with no copying. The hybrid measures each level's work (edges to examine). Levels under a threshold T = 105 edges run on 4 CPU cores, directly on the GPU's buffers; bigger levels go to the GPU. A tiny level then costs 1–90 µs on the CPU instead of about 200 µs on the GPU. The threshold was predicted from the measured costs (≈0.2 ms per GPU level vs ≈2 ns per edge on the CPU), and a sweep confirmed it.

Background · part 3

GPU programming concepts

CPU and GPU are built for different jobs

M2 CPU · 8 cores
PPPPEEEE

A few powerful cores with large caches, branch prediction and out-of-order execution. Built to finish one task as quickly as possible (low latency).

M2 GPU · 10 cores · 1,280 ALUs

Many simple arithmetic lanes that run the same instruction together. Built to finish a huge number of small tasks per second (high throughput), and to hide slow memory by always having other work ready.

Kernels and SIMT

A GPU program is a kernel: one function that every thread runs, each with its own thread id. In BFS, thread i might handle frontier vertex i. The hardware runs threads in groups of 32 called simdgroups (NVIDIA calls them warps). The 32 lanes of a simdgroup execute the same instruction at the same time on different data. This model is called SIMT: single instruction, multiple threads.

Divergence

If lanes take different branches of an if, the simdgroup runs both branches one after the other, with the lanes that did not take a branch masked off. Loops are worse: a simdgroup keeps looping until its slowest lane finishes. That is why one hub in a simdgroup stalls the other 31 lanes.

The thread hierarchy

Threads form simdgroups of 32; simdgroups form threadgroups of up to 1,024 threads that can share 32 KB of fast on-chip threadgroup memory and synchronise with a barrier; threadgroups form the grid of one dispatch. Different threadgroups cannot wait for each other within a dispatch.

grid: one dispatch, e.g. 4.8 million threads
threadgroup: up to 1,024 threads · 32 KB shared memory · barriers

Latency hiding and occupancy

A read from main memory takes hundreds of nanoseconds, time for hundreds of arithmetic operations. A CPU tries to avoid the wait with caches and prediction. A GPU instead keeps many simdgroups resident on each core and switches to another one whenever a simdgroup waits for memory. This only works if there is enough parallel work in flight. A road-network BFS level with 2,000 frontier vertices cannot fill 10 cores, so the GPU sits mostly idle and its fixed per-level costs dominate.

Graphs of millions of vertices live in the bottom layer. Whether a kernel is fast depends on how often it can be served from the layers above.

Coalescing and cache lines: why random reads hurt

Memory is moved in cache lines of 64–128 bytes, never single values. When the 32 lanes of a simdgroup read 32 consecutive 4-byte values, the hardware fetches one or two lines: the access is coalesced. When they read 32 scattered addresses (for example the neighbours of 32 different vertices), it fetches up to 32 lines and uses 4 bytes of each.

→ 1 line fetched
scattered
→ up to 32 lines

We measured the effect directly: the GPU streams 95 GB/s sequentially, but random 4-byte reads from a table larger than the 8 MB cache run at only 0.28 billion per second, about 1 GB/s of useful data. Graph traversal is mostly random reads, so this number, not the GPU's arithmetic speed, is the real limit.

Atomics

An atomic operation (add, compare-and-swap, max) reads, modifies and writes one memory location as one indivisible step, so concurrent threads cannot corrupt each other's updates. Atomics on the same address are serialised, so hubs become hot spots. Metal's device atomics only guarantee "relaxed" ordering: each operation is indivisible, but there is no ordering between different addresses. Every kernel here was designed so it needs nothing stronger. Atomic additions of floating-point numbers also happen in an unpredictable order, so their rounding differs from run to run; PageRank had to account for that.

Simdgroup operations

Lanes of a simdgroup can exchange values directly, without going through memory. simd_sum adds a value across all 32 lanes; simd_prefix_exclusive_sum gives each lane the sum of the lanes before it; simd_ballot and simd_or combine yes/no flags into a bit mask. This project uses them to append to queues with one atomic per simdgroup, to build frontier bitmaps without atomics, and to add up in-edges in the vector PageRank kernel.

Parallel building blocks: reduction and scan

Reduction

Combine n values into one (a sum, a maximum). Each threadgroup reduces its part with simdgroup operations and threadgroup memory, then one small second pass combines the partial results. Used for frontier sizes, PageRank's dangling mass and convergence checks.

Exclusive scan (prefix sum)

Turn [3, 1, 5, 2] into [0, 3, 4, 9]: each output is the sum of all inputs before it. It tells every thread where to write or which item it owns, and it underlies load balancing and stream compaction. Our scan was unit-tested on sizes 0, 1 and non-multiples of the threadgroup size.

How a Metal program runs

CPU encodes kernels into a command buffer→ commit: the buffer is queued to the GPU→ GPU runs each dispatch (grid of threads)→ CPU waits, then reads results in shared memory
  • Pipelines. Each kernel is compiled into a pipeline state object. Without Xcode there is no offline shader compiler, so this project compiles the Metal Shading Language source at program start and caches the pipelines.
  • Encoders and dispatches. A compute encoder records dispatches in order. Dependent dispatches inside one command buffer cost about 0.6 µs each; a commit-and-wait round trip costs about 111 µs. BFS needs one round trip per level, because the CPU must read the next frontier's size.
  • Timing. The GPU reports start and end timestamps for each command buffer (kernel time). Wall-clock time also includes the round trips; the results use wall-clock time as the headline, because that is what a user waits for.

Unified memory

On a PC with a separate graphics card, data must be copied over PCIe (roughly 16–32 GB/s) before the GPU can use it. On Apple silicon the CPU and GPU use the same physical memory. Buffers created in shared storage mode are visible to both, so the CPU can read a BFS result, or even run the next level itself, with no copy. This is what makes the hybrid BFS possible.

Memory-bound vs compute-bound

The M2 GPU can do about 3.6 trillion floating-point operations per second but read only about 0.1 trillion bytes per second. A kernel needs roughly 36 operations per byte loaded to be limited by arithmetic. BFS does essentially no arithmetic per edge and PageRank does about one addition per 8 bytes, so both are memory-bound: their speed is set by how many bytes they move, and how randomly. That is why results are judged against bandwidth (the "roofline" idea), and why efficiency is reported as edges per second per GB/s.

Background · part 4

Parallel programming on the CPU

OpenMP

The CPU baselines use OpenMP: a #pragma omp parallel for splits a loop's iterations across threads. Starting and ending a parallel region (fork and join) costs about 20 µs, more than a whole small BFS level, so tiny levels run on a single thread.

Scheduling

Static gives each thread an equal block of iterations up front. Dynamic hands out chunks of 64 as threads become free. Guided starts with big chunks and shrinks them. With skewed degrees, equal numbers of vertices are not equal work, so dynamic and guided win.

Barriers and stragglers

Every parallel loop ends with an implicit barrier: all threads wait for the slowest. A BFS on a road network is ~600 consecutive barriers, so its speed is set by the slowest core at every step.

Performance and efficiency cores

The M2 has 4 fast performance cores and 4 slower efficiency cores. Using all 8 helps when work is plentiful and balanced (LiveJournal), but on the road network the barriers wait for efficiency cores and 8 threads run slower than 4.

To avoid many threads fighting over one shared queue, each CPU thread collects newly found vertices in its own local buffer and copies them into the shared next frontier once per level.

Background · part 5

PageRank in depth

The random surfer

Imagine someone browsing the web forever. On each step, with probability d = 0.85 they click a random link on the current page; otherwise they get bored and jump to a random page. A page's PageRank is the fraction of time the surfer spends there in the long run. Pages linked from important pages become important themselves.

r_new[v] = (1 − d)/n + d · ( Σ over in-neighbours u of r[u] / outdeg[u] + dangling / n ) dangling = total score of vertices with no out-links, spread evenly over all vertices start: r[v] = 1/n for every v; the scores always sum to 1

Dangling vertices

A page with no out-links would trap the surfer and leak score out of the system. Its score is instead spread evenly over all vertices each iteration, so the total stays exactly 1. Pokec has 200,110 such vertices.

Power iteration and convergence

Repeating the update converges to the answer, and the error shrinks by at least a factor of d = 0.85 per iteration. We stop when the total change between iterations (the L1 norm) falls below a tolerance, 10−6 in the main experiments, which takes 44–62 iterations here. The speed benchmark runs exactly 20 iterations and reports time per iteration.

Push and pull on the GPU

Push atomics

Each vertex adds its share r[u]/outdeg[u] to each out-neighbour using atomic float additions. Every edge becomes a random atomic read-modify-write, and a hub's thousands of in-neighbours all hit the same address.

Pull gathers

Each vertex reads its in-neighbours' shares from the transposed graph and sums them: one plain random read per edge and one write per vertex. It was 1.5–4.9× faster than push on every graph.

The pull kernels differ in how threads map to vertices, exactly as in BFS. Scalar uses one thread per vertex: good for uniform low degrees, but hubs stall a simdgroup. Vector uses one simdgroup per vertex, with lanes striding the in-list and simd_sum combining: fast on skewed graphs, wasteful on degree-3 vertices. Adaptive sorts vertices into degree bins once and uses the right mapping for each bin.

Floating-point precision

Metal has no 64-bit doubles, so the GPU uses 32-bit floats, which carry about 7 significant digits. Adding 100,000 tiny equal values (about 10−5) into a running total near 0.46 loses the same low bits every time. On the 100,000-leaf star graph this pushed the error 10× past the allowed tolerance. Two techniques fixed it:

  • Kahan summation keeps a second variable holding the rounding error of each addition and feeds it back into the next one. It only works if the compiler does not "simplify" the algebra away, so all shaders are compiled with fast-math turned off.
  • Aggregated and compensated atomics (push kernel): lanes that target the same vertex first add their values with simd_sum and issue a single atomic; when an atomic addition loses noticeable precision, its exact rounding error is computed and added to a second accumulator.

Jacobi vs Gauss–Seidel

The standard update is Jacobi: every vertex reads last iteration's values, so the order does not matter and the GPU can update all vertices at once. Gauss–Seidel updates scores in place, so a vertex can already use the new values of vertices updated before it in the same sweep. The GAP suite's CPU code does this and needs about 40% fewer sweeps.

On a GPU, vertices in the same wave run at the same time and still read each other's old values. Most of the graph still speeds up, because later waves see earlier ones, but a tightly linked pair processed in the same wave converges only at Jacobi speed. The simulation below shows this on a 1,000-vertex graph that contains one such pair (two vertices that each link only to the other). Two more ideas make the in-place version work. In-place updates do not keep the total at exactly 1, so the scores are rescaled to sum 1 after every sweep. And because in-place sweeps make the change per sweep look smaller than the remaining error, the in-place and Jacobi versions are compared at equal accuracy against the exact answer, never at equal tolerance.

Background · part 6

Locality and vertex ordering

A vertex's id decides where its data sits in memory. If neighbours have nearby ids, reading one brings the others into cache with the same cache line; if ids are random, almost every neighbour read is a cache miss. The same graph can therefore run 2–3× faster or slower depending only on how its vertices are numbered.

Measuring locality

Two numbers per ordering: the average id gap |u − v| over all edges, and the share of edges whose ends fall in the same block of 64 consecutive ids. roadNet-CA's original numbering keeps 61% of edges inside a block; web-Google's keeps 0.01%, which is no better than random.

The orderings tested

  • Original: as the dataset was published.
  • Random: the worst case, a baseline.
  • Degree: hubs first.
  • Reverse Cuthill–McKee (RCM): a BFS from a peripheral vertex that visits low-degree neighbours first, then reversed. It keeps neighbours close together.

The orderings interact with algorithms in different ways. RCM helps PageRank because every gather becomes more local. It hurts bottom-up BFS, because bottom-up stops at the first neighbour that is in the frontier, and RCM puts the vertices that are found last at the start of every neighbour list.

Background · part 7

Measuring and validating

TEPS and GTEPS

Traversed edges per second (Graph500 convention): the number of edges in the source's connected component divided by the BFS time. GTEPS is billions of TEPS. The same numerator is used for every variant, so a bottom-up search that skips edges gets no extra credit.

Averaging over sources

Each graph uses 64 random sources with a fixed seed, the same for every variant. Each source gets one warm-up run and 5 timed runs; the median is kept. Throughput across sources is a harmonic mean, the correct average for rates, so a few fast sources cannot hide slow ones.

Fair conditions

All benchmarks ran on AC power, Low Power Mode off, other apps closed. A run on battery made the CPU about 17% slower, so those numbers were re-measured. Every result row records the code version that produced it.

Bandwidth efficiency

A kernel's bytes moved divided by its time, compared with the measured 95.3 GB/s. For BFS the result is also expressed as millions of edges per second per GB/s of bandwidth, so a laptop can be compared fairly with data-centre GPUs that have 10–30× more bandwidth.

Validation: speed only counts if the answer is right

  • BFS: every vertex's distance must equal the serial CPU reference exactly, for all 64 sources, before any timing is recorded.
  • PageRank: within L1 error 10−4 of a double-precision reference, relative error under 10−3 on the top 1,000 vertices, and scores summing to 1.
  • The references themselves were checked against the NetworkX library (45 of 45 checks; worst PageRank difference 3·10−15).
  • Unit tests run every variant on 8 synthetic graphs: a path, a 100,000-leaf star, a complete graph, a grid, random R-MAT graphs, two components and an empty graph, at several threadgroup sizes.
  • Mutation checks: deliberately broken versions of kernels (a wrong bit position, a missing term, a skipped reset) were run to confirm the tests catch each one.

Approach

Fourteen phases, one question each

The work was split into phases. Each one ended with a clean build, all tests passing, a log entry and a commit, so every number can be traced to the code that produced it. Phases 12 and 13 go beyond the original plan.

  1. Environment and scaffold

    Confirmed the machine's real limits through the Metal API; set up runtime shader compilation.

  2. Graph input

    Streaming converter from SNAP edge lists to binary CSR, using about 4 bytes of RAM per edge so 234M-edge graphs fit in 8 GB.

  3. CPU baselines

    Serial BFS (the reference), OpenMP level-synchronous BFS, and direction-optimizing BFS.

  4. Microbenchmarks

    Measured bandwidth, random-read rate and dispatch cost, the numbers every later result is judged against.

  5. First GPU BFS

    Thread-per-vertex and thread-per-frontier-vertex kernels; established the validation and timing method.

  6. Load-balanced BFS

    Degree-binned kernels (simdgroup or threadgroup per big vertex) and an edge-balanced kernel built on a parallel scan.

  7. Direction-optimizing GPU BFS

    Bottom-up levels on a bitmap frontier with early exit; switching decisions match the CPU version level by level.

  8. Hybrid CPU+GPU BFS

    Small levels on the CPU, big levels on the GPU, sharing buffers through unified memory.

  9. PageRank

    CPU reference in double precision; GPU push, and three pull kernels (scalar, vector, degree-adaptive).

  10. Vertex reordering

    Random, degree-sorted and Reverse Cuthill–McKee orderings, to measure how much locality matters.

  11. Full benchmark and report

    One 73-minute validated run of the whole matrix, 11 figures, the written report.

  12. External baseline: GAP

    Built the GAP Benchmark Suite on macOS and ran it on exactly the same graphs and sources.

  13. In-place PageRank on the GPU

    Gauss–Seidel-style updates, per-graph update order, a fair equal-accuracy comparison.

  14. Fixing the stragglers

    Found that tightly linked vertex pairs stay slow; deferred one vertex of each pair and added a per-vertex stopping test.

Bottom-up does the heavy lifting

On LiveJournal the three big levels examine 17M adjacency entries instead of 82M, and their random reads hit a 600 KB bitmap that stays in cache. gpu_do is 3–5× faster than the best top-down kernel.

Load balancing alone is not enough

Balanced top-down kernels beat the naive one by only 1.5–1.8×, because they are still limited by random reads. On the 100,000-leaf star graph, though, balancing is essential: gpu_edge is 68× faster than gpu_naive.

Results · road networks

600 levels: the GPU pays 0.2 ms per level, the CPU pays microseconds

On the road network the hybrid is, in effect, a CPU BFS: no level is big enough to go to the GPU. Its value is that switching device costs nothing. GAP restricted to the 4 performance cores is equally fast there (21.1 ms vs 22.0 ms).

Pull wins by 1.5–4.9×

Push turns every edge into an atomic update that serialises on hubs. It was also the hardest to make accurate: 100,000 float additions into one hub all rounded the same way until we added simdgroup aggregation and a compensated second accumulator.

Vector for skewed graphs, scalar for roads

A simdgroup per vertex is 1.2–1.7× faster on social graphs but 2.8× slower on roadNet-CA, where 90% of its 32 lanes sit idle on degree-3 vertices. The adaptive kernel picks per vertex and stays within 10% of the best everywhere.

Bigger graphs give higher GTEPS, the opposite of the cache hypothesis

Fair comparison with other hardware: the best BFS reaches 84 MTEPS per GB/s of measured bandwidth (Orkut, hybrid). Normalising by bandwidth is the honest way to compare a 100 GB/s laptop with data-centre GPUs that have 1–3 TB/s.

Our CPU baseline is sound

Our own cpu_do is within 0–2% of GAP's BFS on every graph except web-Google (GAP 10% faster), so the GPU speedups are measured against a strong CPU.

GAP's PageRank exposed a lesson

GAP is 1.5–2.7× faster per iteration than our own CPU PageRank (float data, fused loops), and it updates scores in place, so it needs 29–34 sweeps where Jacobi needs 44–62. It reached convergence first on every graph, which motivated Phases 12 and 13.

Results · extension

In-place PageRank on the GPU: a real gain on some graphs, once compared at equal accuracy

The in-place kernel gpu_pull_gs writes each vertex's new share back immediately. Four things had to be right for it to work:

  • Renormalise every sweep. In-place updates let the total score drift from 1, and that error decayed only by 0.85 per sweep. Rescaling to sum 1 fixed it (error after 20 sweeps on one test graph: 6·10−4 → 9·10−7).
  • Choose the update order per graph. On the road network, vertices are split into 9 colour classes with no edges inside a class and relabelled so each class is contiguous in memory (57 → 29 sweeps). Other graphs use plain id order.
  • Defer one vertex of every tight pair (Phase 13). Pairs that link only to each other and share a GPU wave stayed at Jacobi speed and fooled the stopping test. Moving one vertex of each pair to a second pass cut the worst error on Pokec 20× and on LiveJournal 96×.
  • Compare at equal accuracy. In-place sweeps make the change per sweep look smaller than the remaining error, so the stopping tolerance alone is not a fair comparison. Each run below is the fastest stopping rule whose error against the exact answer is no larger than Jacobi's at tolerance 10−6, in both total (L1) error and top-1000 relative error.

Findings

Eight things this project showed

1. Doing less work beats doing work faster

Direction-optimizing BFS gave 3–5×, more than any load-balancing scheme. Skipping edges matters more than processing them quickly.

2. Random reads set the ceiling

About 0.3 billion random reads per second on both CPU and GPU. Kernels that turn random reads into cached or sequential ones win; the rest are stuck.

3. Synchronisation can dominate

A GPU level costs ~0.2 ms however small. On the 600-level road map, GPU BFS spends three quarters of its time waiting: 113 ms end to end for 27 ms of GPU work.

4. Unified memory makes hybrids free

Moving a level between CPU and GPU costs nothing, so each level can run where it is cheapest. That gave 5.1× on roads and 1.2× on social graphs.

5. The best kernel depends on the graph

Vector for skewed degrees, scalar for uniform low degrees, adaptive when unsure. No single kernel won everywhere.

6. Vertex labels are a hidden variable

Random labels cost 2–3×. The order that helps PageRank (RCM) hurts bottom-up BFS, because it changes when early exits happen.

7. The algorithm matters as much as the hardware

Until the in-place GPU kernel existed, GAP's in-place CPU PageRank reached convergence first on every graph. Choosing Gauss–Seidel over Jacobi was worth as much as the GPU itself.

8. Parallelism changes what an algorithm means

On a GPU, "in place" only helps across waves. Diagnosing the exact vertices that lagged (a 2-cycle in Pokec) led to a targeted fix and a fairer stopping test.

Conclusion

What it adds up to

On a laptop GPU with 95 GB/s of memory bandwidth, a careful BFS reaches 4.6–8.0 billion edges per second on social networks, 1.7–2.3× faster than the best CPU code on the same machine and 41–46× faster than a serial search. The gains came from three ideas: skipping work (direction-optimizing), running each level where it is cheapest (the unified-memory hybrid), and matching the kernel to the degree distribution.

PageRank told a more modest story. The GPU computes each iteration 1.0–2.6× faster than GAP, but GAP's in-place updates need fewer iterations. Bringing that idea to the GPU required understanding exactly which vertices converge slowly in parallel and why; with that understanding the in-place kernel beats our best Jacobi kernel on some graphs at equal accuracy, while the sequential CPU algorithm keeps an edge on others.

The broader lesson is that on memory-bound problems the hardware sets the ceiling, but the algorithm and the data layout decide how close you get to it.

Limits & next steps

What is not covered

Limitations

  • One machine, one benchmark run per configuration; run-to-run variation is about 5–10%.
  • Graphs up to 234M edges, the limit of 8 GB with a 3 GB process budget.
  • GPU PageRank uses 32-bit floats; results are accurate to the stated tolerances, not bit-identical.
  • GPU BFS still synchronises with the CPU once per level.
  • GAP's PageRank computes a slightly different vector (no dangling redistribution), so only its timing is compared.

Next steps

  • Run several BFS levels per GPU submission (indirect dispatch) to remove the per-level round trip.
  • Sort each adjacency list hub-first while keeping RCM labels, to get both PageRank locality and fast bottom-up exits.
  • Pin OpenMP to performance cores for barrier-heavy phases.
  • Extend straggler deferral from pairs to short cycles, and compress the CSR to fit larger graphs.
Reproduce

Run it yourself

Everything needed is in the repository: code, scripts, raw CSV results and the written report. Data is downloaded from SNAP and is not committed.

brew install libomp
./scripts/download.sh                 # six SNAP datasets, about 1.3 GB
./scripts/setup_python.sh             # analysis environment
make && make test                     # zero-warning build, 25 test groups
./scripts/run_all.sh                  # full validated benchmark, about 75 minutes
./scripts/run_all.sh gs               # in-place PageRank study
./scripts/gap.sh                      # GAP baseline on the same graphs
.venv/bin/python analysis/plots.py    # regenerate all figures
